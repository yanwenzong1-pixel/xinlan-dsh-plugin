# 派单（y-task-distribution-auto）

把任务从**调度点 A** 派给另一个会话执行，并且**用收据证明送达**。
本技能把「派单」这个动作收敛成**一条命令**：手动往 `outbox/` 丢文件、手写文件名、凭感觉认为"发出去了"——这些全部禁止。

**一分钟速查**（在仓库根目录执行）

```powershell
# 1) 派单前体检（只读，不写任何文件）
node skills/y-task-distribution-auto/scripts/relay-dispatch.mjs check

# 2) 干跑：只打印"会发给谁、发什么、文件名是什么"，不落盘（默认行为）
node skills/y-task-distribution-auto/scripts/relay-dispatch.mjs send `
  --to B --kind dev --id REQ01-dev-r1 --file local/req01-indicators-dev-prompt-20261003.md

# 3) 真发（必须显式 --confirm；发完等收据，看到 SENT 才算送达）
node skills/y-task-distribution-auto/scripts/relay-dispatch.mjs send `
  --to B --kind dev --id REQ01-dev-r1 --file local/req01-indicators-dev-prompt-20261003.md --confirm

# 4) 看台账：谁在等回函、谁已回函、有没有卡住的
node skills/y-task-distribution-auto/scripts/relay-dispatch.mjs status
```

## 〇、范围（只干这一件事）

**做**：把一条已经写清楚的派单（需求号 + 规格文件 + 判据 + 边界）交给指定槽位，并确认送达。

**不做**：
- 不替你想需求内容 —— 派单规格由你（或本会话）先写好，脚本只负责**送**；
- 不自动重发 —— 没收据先查原因，**禁止**换汤不换药地再发一遍；
- 不唤醒离线会话 —— 目标不在线就**拒绝派单**（见铁律 4）；
- 不做产品/文案改动 —— 那是被派出去的任务本身。

**槽位与角色边界**（脚本按这张表硬拦）

### 1.1 标准默认拓扑：**7 个对话**（新环境复刻与技能默认口径，2026-10-28 用户确认）

```
用户
 └─ U 💬 用户决策（唯一入口，只与用户对接）
     └─ A ⌛️ 待办维护（调度点，唯一派发方）
         ├─ B 🏭 插件生产 ①   （dev/ops）
         ├─ F 🏭 插件生产 ②   （dev/ops，与 B 并行）
         ├─ C ✈️ 发布 Release  （只收 release）
         ├─ E 💥 崩溃报告      （crash/ops，同时是 CR 崩溃简报的目标会话）
         └─ G ⬆️ GitHub 投研仓 （git）
```

- **计数**：U + A + 2 个生产 + 1 个发布 + 1 个崩溃 + 1 个 GitHub = **7 个对话**。
- 这 7 个是**最小可用链路**：需求从 U 进、A 派、生产/发布/崩溃/GitHub 各司其职，覆盖"开发 → 发布 → 出事 → 入库"全环。
- **同一件活只派一个生产槽位**；一件任务与它的追加件（`-adN`）必须回同一个槽位。
- **本机在默认之上有扩展**（见 §1.2）：第三生产 `I`、行情服务端 `D`、行情仓 `H`、用户中心 `J`，以及诊断位 `T`。
  扩展槽位**不属于默认口径**，新环境复刻时不必照搬；本机之所以有，是业务长出来的。

## 二、十二条铁律（血账，违反必返工）

1. **不确认收据 = 没发出去。** 写入 `outbox/` 只是"投进邮筒"。必须看到 `state/<名>.done` 内容为 `SENT -> <槽位>`，
   且原件已从 `outbox/` 挪进 `sent/`，才允许说"已派单"。

2. **同一个文件名**永远**只投一次**。收据是 `wx` 写一次（`lib/index.js:132`），启动时把 `state/*.done` 全读进去重表（`lib/index.js:88-90`），
   tick 里 `done.has(fname)` 直接 `skipped += 1; continue`（`lib/index.js:197`）——**静默跳过，连日志都没有**。
   ⇒ 重发必须换新文件名（派单号加 `-r2`）。**`FAIL` 收据同样会永久挡住同名重发** —— 修好原因后也要换名。

3. **文件名不合规范 = 石沉大海。** 正则不匹配的文件在 `outbox/` 里被 `continue` 掉（`lib/index.js:198-199`），
   没有日志、没有收据、文件一直躺在那里，**看起来像在排队，其实永远不会发**。脚本用 `status` 把这类"孤儿文件"单独列出来。

4. **目标不在线就别发。** 插件只认 `ctx.agents.get(id)` 命中的**在线** agent（`lib/index.js:148-149`），失败原因 `no-live-agent`；
   重试 6 次（≈30 秒）后写 `FAIL` 并把原件扔进 `failed/`。**没有冷会话唤醒这条路**。
   ⇒ 脚本在派单前用花名册校验 `live=true`，不在线直接拒绝，并告诉你去把那个会话打开。

5. **重试计数只在内存里**（`lib/index.js:86` 的 `Map`）：宿主一重启就归零。所以"等 6 次失败"不是可靠的排队机制，别拿它当队列用。

6. **角色错配是最高危的错误操作**：把开发需求发给发布会话（或反之）会绕过对面会话的范围纪律（全局规则 §七），
   并且对方**真的会去执行**。脚本用 `--kind` 与槽位做硬匹配，不匹配直接拒绝，不给"就这一次"的口子。

7. **派单号必须唯一且可追溯**：格式 `<需求号>-<短名>-r<轮次>`（例 `REQ01-dev-r1`、`N06-release-r2`）。
   回函文件名必须**含派单号**，否则台账对不上账。

8. **消息里必须有判据和边界**：规格文件必须含「判据」和「边界」两节，否则脚本拒绝派单
   （`--no-template-check` 是逃生门，用了要在派单说明里写明理由）。没判据的派单 = 让对方自由发挥。

9. **问题必须前置；派单流程中途不空等人。**（2026-10-04 用户指令 · **长期生效，跨会话**）

   用户原话：「上一轮任务派发中途经历了好几个小时，我已经睡着了，错过了好几次你向我发起的问题卡片，
   所以后续任务派发时候，问题尽量前置，否则有可能会卡住你的派发流程（如果中途 5 分钟无人回复，
   你可以选择最推荐的方案执行，但保留记录在最终的用户报告『下一步必须做』章节内告诉我做了哪些决策）」。

   - **派单开始之前**：把这次派单需要用户裁决的问题**一次性收齐**，用**一张问题卡**问完（`ask_user_question` 一次可带多问）；
     每问**给出推荐项并标「推荐（Recommended）」**，让用户能只回一句。
     **凡是能从代码/实测/台账自己定的，自己定完直接写进规格**，不要塞进问题卡。
   - **流程一旦开始**（`check` → 干跑 → `--confirm` → 等收据 → 收函）**不再弹新问题卡**；
     缺信息就用**规格里写明的默认值**继续，并在规格中标注"默认值来源"。
   - **5 分钟兜底**：确有必要中途提问时，**5 分钟无人回复 ⇒ 取最推荐的方案继续执行**，不空等、不反复追问。
   - **留痕（必做，三处）**：① 决策写进当轮台账（`local/todo-ledger.md`；派单相关另见 `local/protocol/dispatch-ledger.jsonl`）；
     ② 在规格/回函里注明"此项按推荐方案**代决策**"；③ **最终汇总报告的 `用户下一步必须做` 章节逐条列出"我替你做了哪些决策"**，
     含**决策内容 + 依据 + 如何推翻**，供用户复核。
   - **兜底不适用（必须前置，无回复就停着）**：**不可逆或对外**的动作 —— **外发/上报材料、删除数据或现场、发布上线、花钱**。
     这类问题**必须在开始前问到答案**；没回复就**停在那里不做**，并把"等你一句话"写进最终报告。

10. **提问与重启一律经 A 汇总（2026-10-09 用户指令 · 长期生效，跨会话）**

    用户原话：「所有向用户提问的问题，都以回函的形式统一汇总到你这个待办会话再向我提问，别的会话不要单独问我问题」
    「如需要重启，我已授权本次重启」。

    - **执行方不许直接向用户提问** —— 包括重启授权、口径裁决、要不要删东西、要不要发布。一律写进**回函**的
      「需要调度点裁决的问题」一节，由 A 汇总后**统一向用户提问**（用户只看 A 的问题卡）。
    - **重启**：执行方**先请求 A**（写进回函或回函级追加件）；由 A 按用户授权统一决定发起时机与执行方。
      A 若已持有用户授权，会在派单/追加件里**逐字写明「本次重启已授权」**，执行方据此执行，并在回函里写明
      kill 的 PID / 新起 PID / 不可用窗口实测秒数。
    - **违反即返工**。已发生一次：2026-10-09 13:41 生产槽位直接向用户请求重启（用户随即下达本条指令）。

11. **禁止回合内 sleep 等待；等待监控必须交给子代理或定时任务（2026-10-27/28 用户指令 · 长期生效）**

    用户原话要点（两次）：
    ①「A 在回合内用 pwsh Start-Sleep 轮询回函，导致回合被长时间占住、消息积压 12 条」；
    ②「需要 sleep 监控的任务，必须由对话开启子代理去做，不要阻塞对话执行下一个任务；也可以用定时任务」。

    - **禁止**在任一工具调用里用 `Start-Sleep`（或等价手段）等待数据刷新、回函、部署结果、下一次自然刷新。
    - 需要「等待后复查」的任务，**二选一**：
      - **子代理 + 后台 job**：`subagent` / `subagent_fork`，或 `pwsh run_in_background`；
      - **定时任务**：`schedule_create` 预约复查时刻（**推荐**，适合定时窗口与自然刷新）。
    - **派发/启动后主对话立即结束回合**；结果由 relay 注入或定时提醒开启新回合处理。
    - 若发现当前存在回合内 sleep 的监控，**立即改造**并报告：sleep 了多久、积压了哪些任务、改成哪种方式、恢复计划。
    - 细则见 `local/protocol/AGENTS.md` §十五、§十六 16.1（根 AGENTS.md §二十）。

12. **新任务默认只入待办；未写「立即」不得即时派发（2026-10-28 用户指令 · 长期生效）**

    用户原话要点：「发起新任务时，如果没有说明『立即』派发、现在派发、马上处理、现在就修复等明确现在就要派发的指令，
    一律生成待办任务放到待办清单，不要询问用户是否现在派发；用户要马上处理会自己说清楚」。

    - 未出现「立即 / 现在 / 马上 / 立刻就修复」等**即时指令** ⇒ **只写入待办清单**（`local/todo-list-simple.md` 的 §二 / §三），
      **不派单、也不追问「要不要现在派发」**。
    - 只有明确即时指令才立即派发；派发后按铁律 11 结束回合，不 sleep 等回函。
    - 回函/汇报里写明本单属于「**即时派发**」还是「**已入待办**」，便于用户核对。
    - 细则见 `local/protocol/AGENTS.md` §十六 16.2（根 AGENTS.md §二十）。

## 三、标准流程

```powershell
# 仓库根：优先环境变量 DSH_REPO_ROOT，否则读 automation.config.json 的 paths.repoRoot
$Repo = if ($env:DSH_REPO_ROOT) { $env:DSH_REPO_ROOT } else { (Get-Content .\automation.config.json -Raw | ConvertFrom-Json).paths.repoRoot }
Set-Location $Repo
$D = "node skills/y-task-distribution-auto/scripts/relay-dispatch.mjs"

& $D check                                                    # ① 体检：通道/槽位/在线/角色
& $D send --to B --kind dev --id REQ01-dev-r1 --file <规格.md> # ② 干跑：核对"发给谁 + 发什么"
& $D send --to B --kind dev --id REQ01-dev-r1 --file <规格.md> --confirm   # ③ 真发 + 等收据
& $D status                                                   # ④ 台账：待回函 / 已回函 / 卡住
```

**判据（每一步看什么）**

- ① `check` 退出码 **0**，结论行 `PASS`。`❌` 是**硬问题**（槽位没绑定 / 槽位标题与角色不符 / 转发插件没在跑 / 花名册缺失）⇒ 先解决再派；
  **`⚠️ 离线` 不是硬问题**：宿主重启后窗口没打开很常见（2026-10-04 实测重启后只剩 2/7 在线），它只影响那一个槽位 ——
  要派给它就会在 ③ 被拒，派给别人不受影响。看 `可派单槽位:` 那一行决定能不能派。
- ② 干跑打印**目标会话标题 + 会话 id + 文件名 + 正文摘要 + 字节数**。标题不是你要找的那个会话 ⇒ 停下来。
- ③ `--confirm` 后必须出现 `✅ 已送达`（`SENT -> <槽位>`）；若 `❌ FAIL`、`⏳ 超时` ⇒ 按 §五 对照表处置，**不要重复写同名文件**。
- ④ `status` 里这条派单应出现在「待回函」；对方把回函写进 `inbox/reply-<派单号>.md` 后，它转到「已回函」。

## 四、派单规格模板（照着填）

模板文件：`templates/dispatch-spec-template.md`。**五节缺一不可**（另有第六节「回合纪律」，见下）：

> 模板首部固定带「**开发模式：Ponytail full**」默认约束（AGENTS.md §十六）：需求精化 → 逐条合理性校验 → 改前取证 → 原子步骤 → 先红后绿 → 真机验证 → 写回证据。派单方**不得删除**这一行；任务形态不适用时，在规格里写「Ponytail full 适用性：裁剪哪几步 + 理由」。

| 节 | 写什么 | 反面例子 |
|---|---|---|
| 任务号 / 背景 | 这条需求从哪来、为什么现在做 | 「之前说的那个」 |
| 要做什么 | 动哪个文件/哪个接口的什么行为，可逐条勾 | 「优化一下」 |
| 判据 | **可执行**的验证：命令 + 期望输出/退出码，或 file:line 证据 | 「测试通过」 |
| 边界 | 只允许改哪些文件/目录；明确不做什么 | 不写 ⇒ 对方会顺手重构 |
| 回函要求 | 回函文件名（含派单号）+ 必须附的证据（命令、退出码、N/N） | 「做完了说一声」 |
| **回合纪律**（2026-10-28 新增，模板必带） | 写清「本单不需要回合内等待」+「回函后由 A 在新回合处理」；若任务确需等待数据刷新，写明用**子代理/后台 job/定时任务**，不得写"等 N 分钟后继续" | 「出结果后告诉我」（诱导对方 sleep 轮询） |

派单消息由脚本拼装，结构固定：

```
【派单 <派单号>】A（调度点） → <槽位> <会话标题>
类型: <kind> / 规格文件: <绝对路径>（sha256:<12位>，<字节> 字节）
回函: 把回函写进 <协议目录>\inbox\reply-<派单号>.md（文件名必须含派单号）
派单时间: <本地时间>

──── 规格正文 ────
<规格文件内容；超过 8000 字节时默认只带摘要 + 指针>
```

## 五、失败与异常对照表

| 现象 | 真实含义 | 处置 |
|---|---|---|
| `❌ 拒绝派单：目标不在线` | 那个会话没开 | 让用户打开该会话 → 重跑 `check` → **用同一个派单号**再发（此时还没写盘，无副作用） |
| `❌ 拒绝派单：角色/类型不匹配` | 例如 `--to C --kind dev` | 换槽位改 `--kind`；发布类任务才进 C |
| `❌ 拒绝派单：同名收据已存在` | 这个文件名已投递过（含 FAIL） | 换派单号：`-r2`；**先看回函**再决定要不要再派 |
| `⏳ 超时（未拿到收据）` | 文件已在 `outbox/`，插件还没投出 | 等 10 秒重跑 `status`；**绝不重复写同名文件**；仍无收据 ⇒ 查 `/relay/state` 的 `lastError` 与 `relay.log` |
| `❌ FAIL` 收据 | 投递失败且已放弃（原件在 `failed/`） | 读收据里的原因 → 修因 → 换号重派 |
| `status` 报「孤儿文件」 | 文件名不合规范，永不会被投递 | 删掉它，用脚本重新发（新号） |
| `check` 报「槽位 X 离线」 | 那个会话窗口没打开（宿主重启后常见，**不是故障**） | 派给别人不受影响；要派给 X 就先打开那个会话，再重跑 `check` 看 `可派单槽位:` |
| `check` 报「标题与预期角色不符」 | 槽位绑定可能指错了会话（**硬问题**） | 核对 `session-map.json` 与该会话标题；确有把握才用 `--force-title` |
| `check` 报「状态文件过期」 | 转发插件可能没在跑（宿主重启后没起来） | 查 `relay.log` 有没有新的 `START`；必要时走标准通道重启 |
| 收据有、对面说没收到 | 极少数：注入成功但对方会话未落盘 | 让对方会话把最近一条消息贴回来核对；同时看 `relay.log` 的 `SENT` 行 |

### 6.1 台账口径：三类记录怎么分（2026-10-11 定）

`check` 与 `status` 的台账由**台账 SENT 记录 + `state/` 收据**合并而成，分三类，**只有第一类要回函**：

| 类别 | 怎么认 | 算不算「待回函」 | 算不算「已送达」 |
|---|---|---|---|
| **派单** | 记录 `id` 不以 `reply-` 开头 | **算** | 算 |
| **回函登记** | 记录 `id` **以 `reply-` 开头** —— 它是**已经投递给 A 的回函**（例 `sent/to-A-reply-crash-*.md`），只是长得像派单 | **不算** | **算**（没投出去过才算没送达，不能从总数里删） |
| 收据 / 文件（判回函的证据） | `state/*.done` 与 `sent/`、`inbox/` 里的文件 | —— | —— |

汇总行的现行写法（**逐字**，脚本原样打印）：

```
派单台账: 已送达 549 条 / 其中待回函 19 条（另有 3 条为「回函登记」，不计入待回函）   （台账 + state/ 收据合并口径）
```

没有回函登记时，括号那段不打印（老写法保持原样）。

**判「已回函」的两个证据**（缺一不可地都要查）：

1. **收据**：`state/` 里该号对应的**回函收据** —— 归一化掉 `outbox-` 前缀后，接受 `reply-<派单号>[.md|-后缀]`
   与 `inbox-reply-<派单号>[.md|-后缀]` 两种写法（两份都认，因为收据名带不带 `.md` 是历史写法差异）；
2. **文件**：`sent/reply-<派单号>*.md` 或 `inbox/reply-<派单号>*.md` 在盘（收据可能因中继重启/写失败而缺）。

> ⛔ **投递收据不是回函**：`state/to-<槽位>-<单号>.md.done` 与 `state/outbox-to-…done`（内容 `SENT -> X`）
> 只证明**投出去了**。把它们当成"回来了"，会让**全部已送达**（现 549 条）瞬间被判成已回函、「待回函」直接归零 ——
> 这种"宽松过头"比误报更危险。这条口径有**反向用例**钉住（改宽了自检会红）。

## 九、术语（说人话）

- **派单**：把一条任务发给另一个会话去干，本会话只做调度。派完就结束回合，回函由 relay 注入新回合处理（不在回合内 sleep 等回函）。
- **槽位**：默认 **7 个对话** = U（用户决策）+ A（待办维护）+ B/F（生产）+ C（发布）+ E（崩溃）+ G（GitHub）；本机另有扩展槽位 I/D/H/J 与诊断位 T（共 11 个可派单 + 1 个诊断）。改 `session-map.json` 里的对应关系 5 秒内生效。
  T 是诊断位（只跑通道自检），E 收崩溃简报与宿主故障取证。
- **U（用户决策）**：唯一用户入口；只把用户需求原样转给 A、把 A 的消息转给用户；只能派单给 A；
  收到 A 的完成/状态消息后，同一轮清理待办清单（§13.8）。
- **收据**：转发插件投递成功后写的一个小文件，内容是"发给了谁"；**它是"已送达"的唯一凭据**。
  **它不证明对方回了函** —— 判回函只看带 `reply-` 标记的收据或文件（见 §6.1）。
- **回函登记**：记录里 `id` 以 `reply-` 开头的那一类 —— 是**已经投给 A 的回函**在台账里的样子，
  它长得像派单，但**不要**再等它回函。
- **回函**：被派单的会话干完活写回来的答复文件，落到 `inbox/`，插件把它投给 A（本会话）。
